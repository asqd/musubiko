# План тестирования

Цель — проверить, что Musubiko говорит правду о ветках и что ни одна операция не теряет работу:
всё, что сделано, отменяется, а отмена не трогает чужое.

Исходная точка (12.10.2026): `make test` — 79 тестов ядра на временных репозиториях, все
зелёные. Тестов интерфейса нет, CLI и Tauri-команды отдельно не тестируются, производительность
не замеряется автоматически.

Решения:

- Интерфейс тестируется через мост для разработки (раздел 3) во встроенном браузере.
- `leveltravel` — только чтение; меняющие операции — только на стенде.
- Сначала весь план и список найденного, потом исправления по выбору.

Порядок: стенд → сверка статусов с git → «операция + отмена» и сбои → CLI → скорость → мост и
интерфейс → сборка.

## 0. Стенд — готов

`make sandbox` (или `scripts/sandbox.sh [папка]`) за ~10 секунд собирает стенд в
`/tmp/musubiko-sandbox` — вне любого репозитория, иначе git находит его из `not-a-repo`. Каждый
запуск собирает заново. Скрипт изолирован от глобального конфига git. В папке стенда:
`README.md` — что за репозиторий где, `expected.tsv` — какой статус и какую базу приложение должно
показать для ключевых веток (строки без статуса — заметки для радара и баз).

Что в нём:

- `origin.git` — bare-репозиторий вместо сервера; `me/` и `colleague/` — два клона с разными
  `user.email`, чтобы были «мои» и «чужие» ветки.
- **flow** (master + develop): ветки слита / squash / rebase / конфликт / не слита; отстающий
  локальный develop; незапушенные коммиты; ветка только на сервере; ветка с удалённым upstream;
  неделя без коммитов (`GIT_COMMITTER_DATE`); база ушла вперёд на 20+ коммитов.
- **хотфиксы** во всех состояниях радара: пара перенесена cherry-pick'ом; перенесена squash'ем;
  `-dev` нет; в master есть коммит, которого нет в develop; пара, где cherry-pick даст конфликт.
- **дифф**: переименование, бинарный файл, большой и сгенерированный файл, только пробельные
  изменения, файл без перевода строки в конце, CRLF, кириллица и пробелы в путях.
- **странные репозитории**: без develop; master и main одновременно (с `origin/HEAD` и без);
  пустой; detached HEAD; посреди rebase/merge; shallow-клон; с подмодулем; открыт worktree;
  есть stash; ветки `a` и `a/b`-подобные коллизии имён, тег с именем ветки, длинные и русские имена.
- «Сломанный сервер»: `origin` указывает в несуществующую папку; `pre-push` хук, который падает;
  `push` отклоняется, потому что ветку на сервере успели сдвинуть.

Реальный большой репозиторий — `~/Documents/workplace/leveltravel` (845 refs, есть develop):
только чтение, для правдоподобности статусов и замеров скорости.

## 1. Ядро (Rust)

1. Пройти по модулям `core/musubiko-core/src` и сопоставить с `tests/`: что не покрыто.
   Особое внимание — `ops.rs` (шаги и отмена), `port.rs` (перенос и конфликты), `cache.rs`,
   `repo.rs` (выбор git и базы).
2. **Сверка статусов с «голым» git** (главный оракул) — сделано, `scripts/check-statuses.py REPO
   [--base B]`. Итог: 13 репозиториев стенда против develop, master и пяти произвольных баз;
   `leveltravel` — 841 ветка против develop и master: расходится только находка 1. Отдельно
   проверено то, где git и Musubiko ошибались бы вместе: shallow против полного клона
   (находка 4), устаревание кэша после слияния на сервере и amend, испорченный и недоступный кэш —
   работает.
3. **Операция + отмена = ничего не произошло** — сделано, `tests/undo.rs`. Снимок: все refs
   здесь и на сервере, HEAD, рабочая копия с содержимым и неотслеживаемыми файлами, stash,
   worktree, локальный конфиг, папки рядом с репозиторием. 18 сценариев: hotfix (остаться,
   worktree, переключиться; с push и без; с изменениями и без), новая ветка (свежая и локальная
   база, от ветки, от ветки только на сервере), checkout (stash, worktree, ветка только на
   сервере), перенос в существующую и в новую `-dev`, удаление (одной, многих, только на
   сервере). Отмена восстанавливает всё, кроме связи с upstream после удаления (находка 7).
   Отменяется копия операции, прошедшая через JSON, как из журнала.
4. **Отмена отказывается, когда должна** — сделано: коллега запушил в новую ветку — ветка на
   сервере цела; поверх нашего stash лежит чужой — оба на месте; на месте удалённой ветки
   появилась новая с тем же именем — не затёрта; в открытой папке-worktree есть работа — папка
   не удалена. Не выдерживает только время: после `git gc` отмена удаления падает (находка 8).
5. **Сбой посередине** — сделано: каждый шаг каждой из 18 операций по очереди падает; «Откатить»
   возвращает снимок, «Повторить» доводит до конца, и такая операция тоже чисто отменяется.
   Настоящие сбои: pre-push хук (текст хука доходит до пользователя), `index.lock`, конфликт при
   переносе — откат удаляет временную папку; конфликт, решённый «взять из коммита», — операция
   доходит до конца и отменяется.
6. Кэш — сделано вместе с пунктом 2 (сброс из палитры проверить в интерфейсе).
7. Выбор git: в `PATH` первым стоит Homebrew 2.37.3 (старее нужного 2.38), приложение верно
   берёт `/usr/bin/git` 2.39.5. Осталось проверить понятную ошибку, когда подходящего git нет
   совсем (см. находку 3).
8. `cargo clippy --workspace -- -D warnings` и `npm run typecheck` — без замечаний.

## 2. CLI

Все подкоманды (`branches`, `info`, `diff`, `conflicts`, `hotfix`, `radar`, `where`) на каждом
репозитории стенда: не падают, код возврата осмысленный, ошибки читаемые. `hotfix` без `--run`
ничего не меняет в репозитории (сравнить снимки). Вывод сверить с тем, что показывает приложение.

## 3. Интерфейс

Нативное окно Tauri на macOS автоматизировать нечем (WebDriver для WKWebView нет). Варианты:

- **Мост для разработки** (предлагаю): интерфейс из `vite` открывается в обычном браузере, а
  `invoke` в dev-режиме уходит по HTTP в маленький сервер, который вызывает те же функции ядра.
  Тогда я сам прохожу все экраны во встроенном браузере на настоящих репозиториях стенда,
  делаю скриншоты и читаю консоль. Нативные вещи (диалог выбора папки, меню, буфер обмена,
  открытие в Finder) проверяются отдельно вручную.
- Ручной чек-лист: вы кликаете по пунктам ниже в `make dev`, я разбираю найденное.

Сценарии по экранам:

- **Открытие**: «Добро пожаловать», недавние, не-git папка, папка внутри репозитория, пустой
  репозиторий, удалённый с диска репозиторий из недавних.
- **Ветки**: каждый статус и его подсказка; хотфикс-пары рядом; все фильтры, их сочетания с
  поиском `/`; «Сравнивать с» — поиск, недавние, произвольная локальная ветка; ⌘R и обновление
  при возврате в окно; 845 веток — прокрутка и отклик.
- **Дифф**: дерево файлов, unified/split, подсветка, разворот скрытых строк, «Просмотрено»
  (и сброс после нового коммита), `-w`, бинарные/большие/переименованные, `j`/`k`/`v`/Esc,
  вкладки «Коммиты» и «Конфликты».
- **Мои ветки**: причины «требует внимания», выбор коллеги, фильтры, массовое удаление слитых,
  счётчик в левой панели.
- **Карточка ветки**: статусы против master/develop/выбранной базы, checkout, удаление,
  новая ветка от этой.
- **Новая ветка ⌘N** и **Новый hotfix**: транслитерация и нормализация имени, подсказки
  префиксов, занятое имя (локально и только на сервере), предупреждения о грязной рабочей копии
  и отставшей базе, показ команд, все три исхода ошибки, репозиторий без develop.
- **Радар**: все состояния стенда, перенос, конфликт при переносе с «взять из ветки/коммита»,
  «Проверить и продолжить», «Пропустить», откат, удаление завершённой пары.
- **Гигиена**: выбрать всё по фильтру, чужие и не слитые требуют подтверждения, текущую и
  базовые выбрать нельзя, «Получить», автополучение по таймеру не мешает операциям.
- **Где коммит?**: хэш, номер задачи (в т.ч. только в имени влитой ветки), текст, ничего не
  найдено, перенос коммита, который есть только в master.
- **Checkout**: worktree и stash, ветка только на сервере, предложение вернуть изменения.
- **Палитра ⌘K**, **журнал** с отменой, свёрнутая панель ⌘B, светлая/тёмная тема.
- **Ошибки**: баннер, «Скопировать отчёт» — домашняя папка заменена на `~`, токен в URL
  `https://user:token@…` заменён на `***`; экран вместо упавшего окна; ротация лога после 1 МБ.

## 4. Скорость

На leveltravel: холодный список веток (заявлено ~14 с против develop, ~42 с против master),
повторный (~0,1 с), после одного нового коммита в базе, «Мои ветки», радар, «Где коммит?»,
дифф большой ветки. Записать цифры как базовую линию, чтобы ловить регрессии.

## 5. Сборка и платформы

- `make app` и запуск `Musubiko.app`: окно открывается, git находится без терминального `PATH`
  (запуск из Finder), репозиторий открывается.
- Windows и Linux: тесты ядра уже идут в CI; установщики проверяются вручную по чек-листу
  (первый запуск, git из Git for Windows, пути с обратными слэшами и CRLF).

| 3 | `git.rs` `discover` | `MUSUBIKO_GIT` не переопределяет выбор: всегда берётся самый новый git из найденных, указанный в переменной побеждает только если он новее. README обещает, что «другой можно указать» | неудобно |
| 4 | статусы | В shallow-клоне у всех веток «Нет общей истории с develop» и бессмысленные ↑↓ (5/3 вместо 1/30): история общая, её просто не скачали. Нужна причина и подсказка `git fetch --unshallow`. Стенд: `shallow` | вводит в заблуждение |
| 5 | `branches.rs` `first_author`, `mine.rs` | Владелец — автор самого раннего *по дате коммита* своего коммита (`git log` без `--topo-order`). После rebase даты одинаковые, и владельцем оказывается не тот, кто начал ветку: на `leveltravel` 6 из 841 веток, например `LT-22277` (начал miv, показан ahiskali1) — и в «Моих ветках» она у другого человека. «Начата» в «Моих ветках» тоже берётся по дате коммита, то есть дата rebase | врёт о владельце |
| 6 | CLI | `musubiko branches --base <нет такой ветки>` не ошибка, а 46 веток с «Нет ветки …»; неизвестный флаг (`--jsn`) молча считается путём к репозиторию. В приложении базу выбирают из списка, так что только CLI | неудобно |
| 7 | `ops.rs` `DeleteLocal` | Отмена удаления возвращает ветку на тот же коммит, но без upstream (`branch.X.remote/merge`): `git pull`/`push` без аргументов в ней больше не работают, и это отличается от состояния до удаления. Тест `delete_*` в `tests/undo.rs` | отмена неполная |
| 8 | `ops.rs` удаление | Удалённые ветки держатся только на том, что git ещё не собрал мусор. Reflog удалённой ветки исчезает вместе с ней, и через ~2 недели (`gc.pruneExpire`) автоматический `git gc` удаляет её коммиты. «Отменить» в журнале падает с `fatal: bad object`, а у неслитой ветки работа пропала. Исправление — держать ref вроде `refs/musubiko/deleted/<операция>/<ветка>`, пока операция в журнале. Тест `undo_of_a_delete_survives_garbage_collection` | теряет работу |
| 9 | `src-tauri/src/journal.rs` (по коду) | Если `journal.json` не разбирается (после отката на старую версию, не знающую нового вида шага, или испорчен вручную), `load` молча возвращает пустой список, и первая же операция перезаписывает файл: вся история отмен пропадает. Стоит отложить нечитаемый файл в сторону (`journal.broken-<время>.json`) и сказать об этом | теряет историю отмен |

## Результат

- Найденные проблемы — список: шаги воспроизведения, ожидаемое и фактическое, серьёзность
  (теряет работу / врёт о статусе / неудобно).
- Каждый исправленный баг закрывается тестом, который падал до исправления.
- Стенд, сверка с git и проверка «операция + отмена» остаются в репозитории и идут в `make test`.
